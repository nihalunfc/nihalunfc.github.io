Day 18. Partitions and backfills

⏱ 4h · learn 65m · lab 135m · ship 25m · review 15m🏷 hospitality, QSRBefore: Day 17

By the end of today you can

  • Partition assets by business date and process one day per run
  • Run and monitor a backfill after a bug fix
  • Handle look-back windows and late data with partitions
  • Use static and dynamic partitions for per-store or per-hotel work

1. Why this matters

"Rerun last month" is a weekly request in real teams: a rule changed, a source re-sent history, a bug was fixed. With partitions it's a few clicks and costs exactly the compute it needs. Without them, it's a frightening one-off script.

2. Daily partitions

import dagster as dg
daily = dg.DailyPartitionsDefinition(start_date="2026-09-01", timezone="America/Toronto", end_offset=0)

@dg.asset(partitions_def=daily)
def stg_qsr_pos(context: dg.AssetExecutionContext, raw: RawZone) -> dg.MaterializeResult:
    bdate = context.partition_key                     # "2026-09-14": business date, passed in
    df = qsr.clean_day(raw, bdate)
    path = f"data/staging/qsr_pos/business_date={bdate}/part.parquet"
    df.write_parquet(path)                            # REPLACE this partition: idempotent
    return dg.MaterializeResult(metadata={"rows": len(df)})

Each partition is materialised and tracked separately. The UI shows a bar of green/red/missing days.

The QSR business day ends at 04:59

Business date 14 Sept includes files in the 14 Sept folder and orders after midnight that appear in the 15 Sept export (depending on how the POS splits files). The partition for 14 Sept therefore needs both folders. Write down which raw inputs each partition reads; that's its dependency window.

3. Backfills

In the UI: select the asset → Materialize → pick a range → launch a backfill. Dagster queues one run per partition (or a single run for the range, if your asset supports BackfillPolicy.single_run() and handles context.partition_key_range). Watch concurrency: 60 parallel runs hitting an SFTP server is a denial of service. Limit with run concurrency settings or tag-based limits.

Maths and principle

Principle: partitioning turns one big function into many small independent ones, so you only recompute what's affected.

Equation: if \(T = \bigsqcup_d T_d\) (disjoint by day) and \(f(T) = \bigsqcup_d f(T_d)\) (the transform works day-by-day), then fixing a bug affecting days \(D' \subset D\) costs \(\sum_{d \in D'} c(f, T_d)\), not \(c(f, T)\).

Analogy: a block-diagonal matrix: each block can be solved on its own. Where it breaks: transforms that need several days (7-day rolling averages, "latest version" across days) aren't block-diagonal. They need a window of upstream partitions, a TimeWindowPartitionMapping, or an unpartitioned downstream asset.

Try it: 365 partitions × 40 s each. Bug affected 20 days. Backfill time with 4 concurrent runs? (20 × 40 / 4 = 200 s.)

5. Static, dynamic and multi-partitions

  • Static: dg.StaticPartitionsDefinition(["H1","H2","H3","H4","H5"]) for per-hotel work.
  • Dynamic: partitions added at run time (a new store opens): dg.DynamicPartitionsDefinition(name="stores"), added by a sensor.
  • Multi: date × hotel: dg.MultiPartitionsDefinition({"date": daily, "hotel": hotels}). Powerful, but the partition count multiplies. 5 hotels × 365 days = 1,825; fine. 500 stores × 3 years = 547,500; not fine. Partition by date and loop stores inside.

The 5-year lens

Partition by business date, not file arrival date: backfills then mean "recompute what we believe about 14 Sept", which is what the business asks. And make every partitioned write a replace (delete-insert or overwrite the folder), never an append. An append-mode partitioned asset is a double-count waiting for its first retry.

Check yourself

1. A partitioned asset appends rows on each run. It's retried once after a timeout. What happens?

Partitioned writes must replace, not append.

2. 500 stores × 1,095 days as a multi-partition. What's the problem?

Keep partition counts in the thousands, not hundreds of thousands.

3. A 7-day rolling average downstream of daily partitions needs which mapping?

Multi-day transforms read a window of upstream partitions.
